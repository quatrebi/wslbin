Variables

Windows variables in your command (PowerShell $env:NAME and $(...), cmd %NAME%) are substituted by
your shell before wslbin starts, in every mode. wslbin then translates paths in the values it gets:
    make VERSION=$env:APP_VERSION
    rsync -av "$(Get-Location)\dist\" host:/srv/       (PowerShell)
    make VERSION=%APP_VERSION%                          (cmd)

Linux variables and commands (--wslbin-sh): $HOME, ${VAR}, $(command), `command` are substituted by
bash. In PowerShell write them in single quotes, or PowerShell takes them first.
    make --wslbin-sh 'OUT=$HOME/out' 'TAG=$(git rev-parse --short HEAD)'
Longer chains: wslbin -c "...".

Windows variables seen by Linux programs
  pass_env = KENV_*, APP_*, CI        in wslbin.ini; * and ? are wildcards, case does not matter.
  - Each matching variable is listed in WSLENV for the call, so the program sees it.
  - A value that is a Windows path, or a list of paths separated by ;, is translated
    (C:\x\y -> /mnt/c/x/y; C:\a;D:\b -> /mnt/c/a:/mnt/d/b). Any other value arrives unchanged.
  - PATH and WSLENV are never passed (a Windows PATH would replace the Linux one).
  - Names you list in WSLENV yourself keep working, with your flags.
  - wslbin never rewrites the environment of wsl.exe itself: it reads SystemRoot, TEMP and the like.
  - See the plan: <utility> --wslbin-explain prints a line "wslbin: env NAME" on standard error for
    each variable (with the value only where a path was translated: values may be secrets).

Directories for programs in WSL
  path = ~/.local/bin, ~/.cargo/bin     in wslbin.ini
  bash is started without your profile (that is what keeps the start fast), so tools installed by
  pipx, cargo or go are not found by themselves. This puts the directories in front of PATH.
